# Catalogue de briques et skill aiguilleur : plan de mise en œuvre

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Le socle porte tout le cours DevOps : une base enrichie, un catalogue `briques/` testé par la CI, et un skill `socle-repo` qui choisit les briques selon le projet.

**Architecture:** Chaque brique est un dossier `briques/<nom>/` (fiche `BRIQUE.md` + fichiers rangés à leur chemin cible). `scripts/ajouter-brique.sh` les copie dans un projet sans rien écraser ; `scripts/verifier-briques.sh` les valide avec des outils en conteneurs épinglés, en local comme en CI (job `briques`).

**Tech Stack:** Bash, GitHub Actions, Docker Compose, Nginx, OpenTofu (kreuzwerker/docker), Ansible, Prometheus/Alertmanager/Grafana/blackbox, ntfy, prom-client, Next.js 16, pnpm, Vitest, ZAP.

**Spec:** `docs/superpowers/specs/2026-11-19-briques-design.md` (décisions 1 à 10 incluses).

**Sources à adapter (jamais copiées telles quelles) :** la solution du TP fil rouge du cours (abrégé `SOL/`), et ma version corrigée du TP (`infra/`) pour l'IaC (version corrigée pendant le TP).

## Global Constraints

- Actions épinglées par SHA complet + commentaire de version (`# vX.Y.Z`) ; reprendre les SHA déjà présents dans `.github/workflows/*.yml` quand l'action y figure, sinon prendre la dernière release via `gh api repos/<owner>/<repo>/releases/latest`.
- `permissions: {}` au niveau workflow, droits minimaux par job, `timeout-minutes` sur chaque job.
- Jamais `${{ github.event.* }}` ni `${{ inputs.* }}` dans `run:` : passer par `env:`.
- Images à version précise (digest pour Postgres et pour les images d'outils de `verifier-briques.sh`), conteneurs non-root quand l'image le permet.
- Dépôt public : aucun secret, aucun nom d'hôte réel, aucune donnée personnelle. Valeurs d'exemple : `exemple.fr`, `deploy`, `203.0.113.10`.
- Commentaires de code sobres (une ligne quand le pourquoi n'est pas évident) ; les explications vont dans `BRIQUE.md`.
- Tout en français (fiches, messages des scripts, noms de jobs), Conventional Commits en français, pas d'emoji.
- Scripts : `#!/usr/bin/env bash` + `set -euo pipefail`, compatibles bash 3.2 (Mac) ; `shellcheck` sans avertissement.
- Ne jamais renommer les jobs requis existants (`actionlint`, `qualite`, `tests`, `build`, `docker`).
- Image publiée par `release.yml` : tags `{{version}}` (sans `v`), `{{major}}.{{minor}}`, `sha`. Le déploiement utilise `{{version}}`.

## Review Focus

1. Un projet qui a déjà modifié un fichier qu'une brique `remplace:` : le script doit s'arrêter (code 4) sans rien copier. Test dans la tâche 1.
2. Une brique appliquée deux fois : message « déjà présente », code 0, aucun fichier touché. Test dans la tâche 1.
3. Un tag de déploiement mal formé passé à `workflow_dispatch` (`v1.2.3; rm -rf /`) : refusé avant toute connexion SSH. Vérifié par un test du script de validation dans la tâche 4.
4. Une route dynamique Next (`/api/taches/42`) ne doit pas créer une série par identifiant : le label `route` est le gabarit (`/api/taches/[id]`). Test dans la tâche 7.
5. Le sujet ntfy et le jeton ne doivent jamais apparaître dans le dépôt : `alertmanager.yml` n'utilise que `url_file` et `credentials_file`. Vérifié par un `grep` dans `verifier-briques.sh` (tâche 8).
